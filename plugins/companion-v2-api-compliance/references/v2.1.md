# API 2.1 Compliance Rules (deltas only)

Applies **only** when the resolved `@companion-module/base` version is **≥ 2.1.0** (Companion 5.0+). Apply `v2.0.md` first; this file lists only what 2.1 adds or tightens. 2.1 has **no runtime breaking changes**, but its TypeScript typings are stricter.

For a **2.0.x** module, do not report anything from this file as required. The only exception is when the module *uses* a 2.1-only feature (see the last section). At most, mention useful items once in the "💡 Available if you upgrade to 2.1" line.

---

## 🔴 Critical — compile errors at base 2.1.x

| Check | Expected in 2.1 |
|---|---|
| Action with `subscribe` | `optionsToMonitorForSubscribe: [...]` is **required** by the types whenever `subscribe` is present. Missing it is a TS error |
| Action without `subscribe` | Must not set `optionsToMonitorForSubscribe` / `skipUnsubscribeOnOptionsChange` (types forbid them without `subscribe`) |
| Advanced feedback (`type: 'advanced'`) | `affectedProperties` is a **required key** at 2.1.3 (`affectedProperties: ['bgcolor', 'color']`, or explicitly `undefined`). Omitting it is a TS error. Allowed values: `'text' \| 'size' \| 'color' \| 'bgcolor' \| 'alignment' \| 'pngalignment' \| 'png64' \| 'imageBuffer'` |
| `CompanionActionDefinition<T>` generic | `T` is now the action **schema** (`{ options: {...}; result?: ... }`), not the options object. `CompanionActionDefinition<{ num: number }>` from 2.0 code fails. Use `CompanionActionDefinition<ActionsSchema['my_action']>` or build via `CompanionActionDefinitions<ActionsSchema>` |
| `hasResult: true` | The schema entry must declare `result: <JsonValue subtype>` and the callback must return it. Conversely, a schema with `result` requires `hasResult: true` |
| Duplicate option ids | Ids must be unique within each action/feedback, and config field ids unique across the config. Companion drops later duplicates (with a warning), so treat this as 🔴 because a field silently disappears |
| Layered presets / composite elements | Strictly validated. Invalid element data shows up as debug-log warnings and broken buttons |
| Manifest `runtime.type` (template rule, not a compile error) | `"node26"`, as in the 2.1 template, with `tsconfig.build.json` extending `@companion-module/tools/tsconfig/node26/recommended.json` (tools ≥ 3.1). A 2.1 module still on `node22` doesn't match its template. In a review, `validate-template.ps1` already reports this as `MAN-RUNTIME`, so don't report it twice |

## 🟠 High

| Check | Expected in 2.1 |
|---|---|
| Advanced feedback with `affectedProperties: undefined` | Companion logs a debug warning for every advanced feedback that does not declare its properties. Declare the real list |
| `context.setCustomVariableValue(...)` in actions | Deprecated ("use the action result flow instead"). Return the value with `hasResult: true` + a `result` schema, and ship `CreateUseActionResultStoreUpgradeScript({ actionId: 'customVariableOptionId' })` (base ≥ **2.1.1**) so existing buttons migrate |

## 🟡 Medium — recommended for 2.1

Report a 🟡 **only where the module has a matching pattern** (e.g. a slow network call in a callback that ignores `context.signal`, a module-specific delay action that `internal:wait` replaces, an advanced feedback that only sets colours). Do not add a finding for every 2.1 feature the module simply doesn't use; collect those, if useful, on a single 💡 line.

- **Abort signals:**
  - Long-running or network action, feedback and learn callbacks should pass `context.signal` to `fetch`/socket calls, or check `context.signal.aborted`, and stop or throw. Thrown errors after abort are ignored, and feedbacks are re-run.
  - Short synchronous callbacks can ignore it, so don't flag those.
- **Action results:** "read/query" style actions that today write to a variable or custom variable are good candidates for `hasResult`.
- **Advanced feedbacks:** prefer boolean or value feedbacks, or layered presets / composite elements, over new advanced feedbacks. Advanced feedbacks are discouraged and likely to be removed in a future major version.
- **`multidropdown` `sortSelection: true`:** use it where selection order should follow `choices` order.
- **Preset feedback-based local variables:** `localVariables: [{ variableType: 'feedback', variableName, feedbackId, options }]`, ideally pointing at a **value** feedback.
- **Preset internal entries:** `internal:wait`, `internal:customLog`, `internal:abortButton`, `internal:localVariableSet`, `internal:checkExpression`, `internal:buttonPushed`, `internal:buttonCurrentStep`, and the building blocks `internal:actionGroup` / `internal:logicIf` / `internal:logicWhile` / `internal:logicOperator` (with `children`). Use them instead of module-specific delay or logic actions.
- **Composite elements:** `setCompositeElementDefinitions({...})` replaces drawing bitmaps in advanced feedbacks. Typing goes through `ModuleSchema.compositeElements`.
- **`static-text` option ids:** may be any string since **2.1.3** (they no longer need to match a schema key). On 2.1.3+ modules, do not flag static-text ids missing from the schema. On 2.0.x–2.1.2 the id **must** be a schema key (e.g. `note?: undefined`), otherwise it is a compile error.

> The list of 2.1-only features that are 🔴 when used by a **2.0.x** module lives in `references/v2.0.md` ("Uses features from a later API version"), because 2.0 reviews never load this file.
