# API 2.2 Compliance Rules (deltas only)

Applies **only** when the resolved `@companion-module/base` version is **≥ 2.2.0** (Companion 5.1+; Companion 5.0.x refuses to load it). Apply `v2.0.md` and `v2.1.md` first; this file lists only what 2.2 adds or tightens. 2.2 mainly adds preset features. It has **no runtime breaking changes**; one typing change (value feedback schemas) can break a TypeScript build.

Some 2.2 items arrived in patch releases. Check the resolved patch version before reporting them:

| Since | Item |
|---|---|
| 2.2.0 | value feedback schema `result`, preset `storeResult`, preset `notes`, CSS colour strings (`CompanionColorValue`) |
| 2.2.1 | `sanitizeVariable()`, `rotation` on composite elements |
| 2.2.2 | `Regex` deprecations (runtime warnings), `Regex.IPV4` / `Regex.IPV6`, `UDPHelper` IPv6 (`family`) |

For a **2.0.x or 2.1.x** module, do not report anything from this file as required. The exception is a module that *uses* a 2.2-only feature: that list lives in `v2.0.md` and `v2.1.md` ("Uses features from a later API version"), because those reviews never load this file. At most, mention useful items once in the "💡 Available if you upgrade to 2.2" line.

The official templates still pin `@companion-module/base` `~2.1.3`. A module on `~2.2.x` has chosen a newer API level on purpose: don't report the base range itself as a template difference. Everything else about the template (Node 26 everywhere, files, scripts) still applies, and `validate-template.ps1` already reports it.

---

## 🔴 Critical — compile errors at base 2.2.x

| Check | Expected in 2.2 |
|---|---|
| Value feedback schema (TypeScript) | Every `type: 'value'` entry in the module's feedback schema (`ModuleSchema['feedbacks']`, `CompanionFeedbackSchema`) must declare `result: <JsonValue subtype>`, e.g. `result: number`, or `result: JsonValue` to keep it untyped. Missing it is a TS error, and the callback's return type must match it. No runtime effect; plain-JS modules are unaffected. `validate-template.ps1 -RunBuild` catches it as a build failure, so don't report it twice |
| `storeResult` on a preset action (TypeScript) | Only allowed on actions whose schema declares a `result` (the types give `storeResult?: never` otherwise) |

---

## 🟠 High

| Check | Expected in 2.2 |
|---|---|
| Preset `storeResult.variableName` | `storeResult: { type: 'local-variable', variableName }` must name a **`simple`** entry in the same preset's `localVariables`. A name that isn't there (or names a feedback-type local variable) means the result has nowhere to go, so the preset doesn't do what its name says. Plain-JS modules aren't type-checked, so also confirm that the action really has `hasResult: true` |
| Variable ids from device data (any 2.x module on Companion 5.1+) | Covered in `v2.0.md` → High ("Variable ids"), because it applies to every 2.x module. For 2.2.1+ modules the fix is `sanitizeVariable(id, replacements?)` from `@companion-module/base` |

---

## 🟡 Medium — recommended for 2.2

Report a 🟡 **only where the module has a matching pattern**. Do not add a finding for every 2.2 feature the module simply doesn't use; collect those, if useful, on a single 💡 line.

- **Deprecated `Regex` patterns (base 2.2.2+):** `Regex.IP`, `HOSTNAME`, `BOOLEAN`, `PORT`, `PERCENT`, `FLOAT`, `SIGNED_FLOAT`, `FLOAT_OR_INT`, `NUMBER`, `SIGNED_NUMBER` and `SOMETHING` are deprecated. Reading one logs a warning in the connection log once per key ("Regex.PORT is deprecated. …"). Replacements:

  | Deprecated | Use instead |
  |---|---|
  | `PORT` | `type: 'number'` with `min: 1`, `max: 65535` |
  | `PERCENT` | `type: 'number'` with `min: 0`, `max: 100` |
  | `FLOAT`, `SIGNED_FLOAT`, `FLOAT_OR_INT`, `NUMBER`, `SIGNED_NUMBER` | `type: 'number'` |
  | `BOOLEAN` | `type: 'checkbox'` |
  | `IP`, `HOSTNAME` | a `textinput` with no regex, so hostnames and IPv6 work; `Regex.IPV4` / `Regex.IPV6` only when the device really needs that family |
  | `SOMETHING` | `minLength: 1` on the `textinput` |

  `Regex.MAC_ADDRESS` and `Regex.TIMECODE` are not deprecated. Changing a **config** field's type (e.g. a `textinput` port to `number`) changes the stored value's type, so the fix needs an upgrade script that converts existing configs (**companion-v2-upgrades**). Mention that in the fix, and check for it in a release that makes the change.
- **A `Regex` key that doesn't exist** (a typo, or `IPV4`/`IPV6` on 2.2.0–2.2.1): the field silently gets no validation. On 2.2.2+ Companion logs "Regex.X does not exist, so is undefined. This is a bug in the module". TypeScript modules fail to build instead.
- **Action results in presets:** a preset that runs a result-returning action (`hasResult`) and then needs the value should use `storeResult` into a `simple` local variable, instead of a module-specific "store to variable" option or a custom variable.
- **UDP and IPv6 (base 2.2.2+):** `UDPHelper` now picks `udp6` for an IPv6 host on its own; a hostname that only resolves to IPv6 needs `family: 'udp6'`. A shared UDP socket (`createSharedUdpSocket('udp4' | 'udp6')`) can only send to its own family. Report this only where the module's config accepts any host (no IPv4-only regex) and it then sends to that host through a hard-coded `udp4` socket, because IPv6 hosts would silently fail.

## 💡 Info — new in 2.2, never required

- **Preset `notes`:** copied to the button when the preset is placed (simple and layered presets). Good for setup hints that today live only in HELP.md.
- **CSS colour strings:** anywhere a colour is accepted (style `color`/`bgcolor`, graphics elements), a module may now give `'#FF0000'` or `'rgb(255, 0, 0)'` instead of a packed number (`CompanionColorValue`). Mixing both forms is fine. Never flag `combineRgb()` or packed numbers.
- **Composite element `rotation`** (2.2.1+): all elements take `rotation` in degrees, -360 to 360.
- **`validateManifest(manifest: unknown, looseChecks)`** now asserts the manifest type and is generated from one zod schema (the same rules as before). Only matters to modules that call it themselves, which is rare.
